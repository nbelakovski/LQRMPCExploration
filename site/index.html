Exploring PID/F, LQR, and MPC

This page explores two control strategies that are more advanced than PID/PIDF: LQR and MPC. LQR (Linear Quadratic Regulator) and MPC (Model Predictive Control) both rely on a model of the system and, in effect, use that model to "be smarter" about controlling the system than PID, which simply reacts to disturbances. PIDF (F for feedforward) sits in between PID and LQR/MPC since it models disturbances like gravity in the feedforward term(s).

In this page I explore using LQR and MPC to control the invtake pivot for 516's 2026 FRC robot and compare them to the PIDF strategy that was actually employed.

To briefly summarize, LQR/MPC both present challenges and opportunities. A big attraction of these methods is more intuitive tuning: you tune Q and R which directly penalize error and control effort respectively, as opposed to P and D which can interact in complicated ways. Another big attraction is that since they require a model, initial tuning can be done before the robot is finished, ideally reducing the amount of time software needs with the robot once it's constructed. Additionally an advantage of MPC is that it can take into account torque limits on the motors and incorporate that into its control strategy.

The biggest challenge with LQR is that modeling is complicated, and it requires a good model to be effective. MPC faces that challenge and additionally faces the challenge that there's no MPC library in Java. In some ways this challenge is an opportunity: a good model can also be used to simulate a PID controller, which would give the benefits of tuning before getting the robot while sticking with a familiar control strategy.

1 · The model

The arm is a rigid body on a shaft, so everything follows from \(T = I \dot{\omega}\). Three torques act on it: the motor, gravity, and friction. Below is the full model, see the appendix for more details and values.

\(\dot{\omega} = (I_{arm} + I_{motor} \cdot \eta \cdot GR^2)^{-1} \cdot (u \cdot \eta \cdot GR - r_{arm} \cdot m_{arm} \cdot g \cdot \cos(\theta) - \mu - b \cdot \omega) \)

Where

\( \omega = \text{Angular rate of arm} \\ \theta = \text{Angle of arm from horizontal} \\ \eta = \text{efficiency} \\ GR = \text{Gear Ratio} \\ u = \text{Motor torque} \\ g = \text{Gravity} \\ \mu = \text{Dynamic friction} \\ b = \text{Viscous friction coefficient} \)

4 · LQR

  

    LQR takes the model we made (more accurately a linearized version of it), along
    with Q and R matrices which specify how much we care about state error and control
    effort respectively (more on those in a minute) and solves the Algebraic Ricatti
    Equation (ARE) to produce an optimal set of gains. Since it's linear you could, in
    principle, extract P and D from the matrix produced by LQR, at least in this case.
  

  

    The Q matrix, put simply, tells the optimization how much we want to penalize errors
    in the angle (that's the Q11 term) and the angular rate (Q22). For this application
    we don't really care that much about angular rate, but we do want the arm to achieve
    its desired target angle with little steady state error, so that's why the Q11 term
    is so high.
  

  

    The R matrix (in this case a scalar since we have 1 control input) tells the
    optimization how much we want to penalize control effort. Often in robotics there's
    a desire to achieve an objective with less effort to save on energy expenditure,
    and so you would set R relatively high to achieve this. For this particular case, since
    we don't move the arm that often, and our drivetrain is a much greater source of
    power draw, I've set R to be fairly low.
  

  

    Notice that with R this low, the controller asks for more control effort than the
    Kraken is able to provide. Try increasing R to get the control effort to a level
    that's realistic. This is an inherent weakness of LQR, it can't take controller
    constraints into account, but MPC can.
  


  

  

    

    

      

      

    

    

    

    

  







  
5 · MPC

    MPC is a broader topic than the name might suggest. There's lots of different
    approaches to the control problem that all fall under the umbrella name of MPC.

    Below is an implementation using the python-control library which uses nonlinear
    solvers. It's accurate, but expensive. In practice one would linearize the
    problem and use a Quadratic Programming (QP) solver which is much faster. There's
    no Java library for MPC, but there are Java libraries for QP solvers that could
    be brought in to run on the System Core.

    MPC generally has the same tuning knobs as LQR, but also one can tune the horizon
    and number of points. Basically MPC will simulate the model up to the horizon and
    it will set constraints at N points along the way (where you specify N). It then
    takes the solution from the first point and applies it.
